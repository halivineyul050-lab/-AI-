# AI 资讯事件聚合与热榜设计

日期：2026-09-29

状态：已通过（2026-09-29）

## 背景

AIHOT 的采编系统把报道归为事件，再按独立信源和时间衰减计算事件热度。泥壳 AI 工具站已有 RSS 自动采编、文章 CMS、新闻列表和文章只读 API，但当前采编每轮最多把 6 条未见来源交给模型，文章记录只保存一个主来源。站内无法查看这篇文章引用了哪些报道，也无法区分单一信源内容与多个站点共同报道的事件。

项目当前新闻页面在 `public/app.js` 中渲染文章列表和详情抽屉；文章持久化在 `articles` 表中，已有的 `source_name`、`source_url` 字段保持兼容。数据库通过 SQLite 与 MariaDB 两种运行路径工作，因此新来源关系需要两种数据库迁移。

## 目标

1. 资讯可以保存并展示本次采编实际采用的全部 RSS 来源。
2. 将一轮采集中的同一事件报道归到一篇资讯，并允许后续来源补充到最近的同一事件。
3. 在现有 `/news` 页面展示近 48 小时多站点热点，并提供只读 API。
4. 复用现有模型采编请求，不为热度计算增加独立的模型调用。
5. 保留 CMS 对文章正文的控制权，并兼容已存在的文章和 API 调用方。

## 非目标

- 不新增 RSS 以外的采集器，不改变现有信源配置和采集周期。
- 不增加向量数据库、向量服务或专用事件服务。
- 不实现日报/周报、信源管理后台、人工校准工作台或通用事件—事实多层模型。
- 不重做工具榜单、工具评分或现有文章 CMS。

## 用户体验

### 新闻页热点区

在 `/news` 现有文章列表上方加入“近 48 小时热点”。每条热点显示排名、标题、不同来源站点数、最新来源时间，以及适用时的“新”“升温”标记。点击后打开现有文章详情抽屉。

当暂时没有至少两个来源站点共同支持的事件时，热点区显示简短空状态；现有新闻列表照常展示单一来源及其它未上榜文章。

### 文章来源

文章详情中的来源区域列出本事件已关联的来源站点、原文标题、原文时间和原始链接。链接只允许 `http` 或 `https`，在新标签页打开并使用 `noopener noreferrer nofollow`。旧文章仍使用现有主来源字段作为回退显示。

## 采编流程

1. 按当前逻辑读取 RSS、筛选未记录的候选项，保留每项稳定 ID、标题、摘要、原文链接、所属 RSS URL 和发布时间。
2. 读取最近 48 小时已发布的至多 10 篇新闻，向现有采编模型提供其 ID、标题和摘要作为事件候选。
3. 同一个结构化模型请求选择一个事件、给出本轮相关来源 ID，并决定新建文章或关联已有文章。来源 ID 和目标文章 ID 均由服务器校验，模型不得提交任意 URL 或任意文章 ID。
4. 新事件按现有文章流程生成并发布一篇资讯；只关联所选的来源项。未选中的 RSS 项继续留待后续采集轮次处理。
5. 已有关联事件只增加来源关联记录，不改写标题、摘要、正文、CMS 修订号或文章状态。若模型无法明确判断为同一事件，则新建事件，避免低置信度合并造成错误归组。
6. 文章和其来源关联应在同一数据库事务中写入。来源关联使用原文链接的 SHA-256 哈希作为稳定键，重复采集只会产生一条记录。
7. 若模型返回空来源集、未知来源 ID 或超出近期候选集的目标文章 ID，本轮不发布、不关联，并记录可诊断的跳过原因。

模型将 RSS 标题和摘要作为不可信的待分析材料，不执行其中要求改变角色、规则或输出格式的文本。模型返回的每个来源 ID 必须属于本轮输入；创建或补充关联前，服务器验证其存在且没有被关联到其它事件。

新增上下文会使现有请求携带更多 token，但不会增加每轮模型请求数。候选新闻上下文最多 10 篇；采编源项仍沿用现有最多 6 条的上限。

## 数据模型与迁移

新增 `article_source_links` 关系表，字段建议如下：

| 字段 | 含义 |
|---|---|
| `source_url_hash` | 原文 URL 的 SHA-256，主键/全局幂等键 |
| `article_id` | 关联的新闻文章 ID，外键删除级联 |
| `source_url` | 原文链接 |
| `source_name` | 来源站点名称；缺少名称时使用规范化主机名 |
| `feed_url` | 采集到此项的 RSS 地址 |
| `source_title` | RSS 项的原始标题 |
| `source_published_at` | RSS 项原文发布时间，可空 |
| `discovered_at` | 本站首次采集时间 |
| `created_at` | 关系记录创建时间 |

主机名统一小写并去除前缀 `www.`，作为来源站点的去重键。同一事件内相同主机名只计一个站点；页面使用“来源站点数”措辞，不将其描述为组织层面的独立性证明。

为适配 MariaDB 的索引长度限制，以 `CHAR(64)` 哈希唯一索引去重，URL 本身保存在非索引文本字段中。按当前工作区可见的版本 18 迁移，新增 SQLite 版本 19 和 MariaDB 版本 19 迁移；实现前再按届时实际迁移头确认编号，不修改既有迁移。

旧文章不批量写入新关系表。若旧文章或 CMS 内容没有关系记录，但 `articles.source_url` 不为空，读取和热度计算时把它作为一个已知来源回退项；不根据旧文章中的“多条来源”文案推断其它链接，也不补造 RSS 标题或原文发布时间。

关系表至少为 `article_id`、`source_published_at` 和 `discovered_at` 建立读取索引。应用层在取得限定的近期来源记录后计算热度，避免数据库方言差异。

CMS 新建或更新的新闻仍可能只写入 `articles.source_url`。读取来源和计算热度时，若关联表没有此主来源，则把它作为单来源回退项；不要求旧 CMS 写入流程同步生成额外关系数据。

## 热度口径

- 时间窗口为 48 小时，证据时间优先使用 `source_published_at`；缺失时使用 `discovered_at`。
- 按文章关联来源的规范化主机名分组；同一主机名在事件内只取最新一条有效证据。
- 每个来源站点的贡献为 `2 ^ (-证据年龄小时 / 24)`，事件热度为窗口内各站点贡献之和。
- 至少 2 个不同站点的事件才进入热点榜。排序按热度降序，热度相同按最新证据时间降序，最多返回 10 条。
- “新”：事件第一条证据在最近 6 小时内。
- “升温”：当前热度比 6 小时前的可比热度上升超过 15%。前值为 0 时显示“新”，不计算百分比。
- “突增”：最近 6 小时首次出现的来源站点不少于 3 个，且占 48 小时来源站点数至少一半。此标记可以和“新”同时出现。
- 热度值用于站内排序，不作为公共 API 的稳定契约，也不要求展示给读者。

热榜通过来源记录即时计算，不另建定时快照表。采集未运行、RSS 发布时间异常或缺少来源数据时，资讯仍可正常阅读，只是不满足热点门槛。

## API 与兼容性

新增 `GET /api/v1/news/hot?limit=10`，匿名只读，复用现有读取速率限制。`limit` 默认为 10，最大 10。响应包含窗口说明、生成时间，以及热点文章的 ID、slug、标题、摘要、排名、站点数、来源名称、最新证据时间和状态标记；不暴露内部提示词或计算细节。

扩展现有 `GET /api/v1/articles/:idOrSlug` 的新闻详情结果，增加 `sources` 数组；原有 `source`、`sourceUrl` 字段及列表 API 的基本结构保持兼容。用户打开详情抽屉时读取该详情接口以取得来源列表；接口失败时仍可展示已有文章缓存和主来源。热点页面和详情抽屉使用同一文章数据及原文链接。

新表查询使用 SQLite 与 MariaDB 都支持的基础 SQL；时间衰减、主机名规范化和热点排序在 JavaScript 中计算，避免引入仅适用于某一数据库的日期或窗口函数语法。

## 风险与处理

| 风险 | 处理 |
|---|---|
| 模型把相似但不同的事件合并 | 只允许匹配输入中列出的近期文章；含糊时新建事件；补充来源不改写 CMS 内容 |
| 模型生成不存在的引用 | 只接受本轮候选 ID，服务器从候选记录取回 URL 和标题 |
| 同一组织使用多个子域 | 第一版按规范化主机名统计并在文案中称“站点数”；后续可按实际信源配置加入显式分组 |
| 旧文章无法还原全部来源 | 只使用已有主来源作为一个回退项；旧数据不参与伪造的多源计数 |
| MariaDB 与 SQLite 行为分叉 | 使用两份版本 19 迁移及同一套应用层热度计算 |

## 完成标准

1. 自动发布的新资讯和关联到旧资讯的来源都能被完整追溯，重复 RSS 项不会重复增加站点数。
2. 文章详情能显示全部已保存来源；旧文章仍能通过原主来源字段显示一个出处。
3. `/api/v1/news/hot` 和 `/news` 展示同一排序结果、相同来源数及标记。
4. 来源数不足两站点的文章不进入热点榜；同站点多条报道只贡献一次。
5. SQLite 与 MariaDB 均可创建迁移后的来源关系表，并保留现有新闻 API 响应字段。
6. 事件关联不覆盖 CMS 编辑的文章正文、状态和修订号。
