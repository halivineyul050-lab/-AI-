- 审查日期：2026-10-19
- 审查范围：`server.mjs`（2664 行）、`backend/`（48 个模块，合计 9780 行）、`public/` 前端主目录（18196 行）、`scripts/`、`deploy/`、`tests/`（178 个测试文件，10615 行）
- 审查方式：静态代码走查 + 本地实机复现 + 并发基准 + 全量测试执行

## 一、总体结论

| 维度 | 评级 | 结论 |
|---|---|---|
| 代码结构与质量 | 中上 | 模块拆分清晰、分层合理，但 `server.mjs` 与若干业务模块存在超长单行/巨型函数，缺少 lint 与类型约束 |
| 安全性 | 中 | 基础防护扎实（参数化 SQL、scrypt、AES-GCM 密钥、SSRF 防护优秀），但存在 **1 个可远程打崩服务的未认证漏洞** 与 2 处数据正确性缺陷 |

**问题分布**：P0 严重 3 项、P1 高 5 项、P2 中 10 项、P3 低 6 项。

## 三、详细分析

### P0-1 畸形请求行导致服务进程崩溃（未认证远程 DoS）

**位置**：`server.mjs:1425`（URL 解析在 `try` 之外，`try` 从 1452 行才开始）

```js
const url = new URL(request.url || "/", "http://localhost");   // 1425，try 之外
...
try {                                                          // 1452
```

**复现证据**（本地实机，Node v22.22.2）：

```
1) 正常请求     => HTTP/1.1 200 OK
2) 畸形请求行   => 连接被直接断开，无任何响应
3) unhandledRejection => TypeError: Invalid URL
```

去掉异常处理器后，同一请求使 Node 进程以 `ERR_INVALID_URL` 直接退出（未打印"进程仍存活"）。

**影响**：任何能访问站点的攻击者发送一行 `GET http://[ HTTP/1.1` 即可让服务下线；systemd 重启窗口内全部用户不可用，且可循环触发形成持续性拒绝服务。这是本次审查中唯一"零门槛、可远程、直接打崩"的问题。

**建议**：把 URL 解析移入 `try`（或先做 `try/catch` 包裹并返回 400）；同时在进程级注册 `unhandledRejection`/`uncaughtException` 兜底并记录后退出，避免任何单请求异常升级为进程退出。

### P0-2 账号注销必然失败 / 删除不彻底

**位置**：`database.mjs:1029` 的 `deleteUserAccount` 只执行 `DELETE FROM users`；`migrations/038_credit_grants.sql:1` 的 `user_id` 带 `REFERENCES users(id)` 却没有 `ON DELETE CASCADE`。

**复现证据**（临时库实跑）：

```
A. 删除仅有钱包/流水的用户 => true
A. 残留 credit_wallets 行数 => 1
A. 残留 credit_ledger  行数 => 1
B. 删除有派发记录的用户 => 抛错: FOREIGN KEY constraint failed
C. PRAGMA foreign_keys => 1
```

**影响**：

1. **功能失效**：注册即赠积分（`verificationGift`）会让几乎所有用户产生 `credit_grants`/钱包记录，注销接口返回 500，用户无法自助注销。
2. **合规风险**：`credit_wallets`、`credit_ledger`、`credit_reservations`、`manual_recharge_orders`、`credit_grants` 均未级联，删除后仍保留用户 ID 与资金流水，个人信息删除不彻底。
3. **双环境行为不一致**：生产 MariaDB 侧这些表没有外键，注销"成功"但留下孤儿数据；本地 SQLite 侧直接报错。同一份代码两种结果，排障成本高。

**建议**：明确注销策略（级联删除 or 匿名化保留账务），统一两侧表定义的 `ON DELETE` 行为，并补一条覆盖"有积分、有充值、有作品"的注销测试。

---

### P0-3 MariaDB 兼容层会改写字符串字面量（静默数据损坏）

**位置**：`mariadb-compat.mjs:83-107`，`translateMariaSql` 用约 20 条正则把 SQLite 语法改写成 MariaDB 语法，不理解字符串边界。

**复现证据**：

```
输入: UPDATE t SET note = 'ON CONFLICT(id) DO NOTHING' WHERE a = MIN(x, y)
输出: UPDATE t SET note = 'ON DUPLICATE KEY UPDATE id=id' WHERE a = LEAST(x, y)
```

**影响**：任何**存储或查询**的文本只要包含 `ON CONFLICT(...)`、`MIN(a,b)`、`JSON_TYPE`、`CAST(... AS TEXT)` 等模式，都会被静默改写。受影响字段包括用户反馈正文、资讯标题/摘要、Skill Markdown、图片提示词、审计日志 diff。改动不可逆且无报错，属于最隐蔽的一类数据事故。

同时该层对 `BEGIN IMMEDIATE`→`START TRANSACTION`、`INSERT OR IGNORE`→`INSERT IGNORE` 的替换也只对"恰好写成这种形式"的语句有效，任何新写法都可能悄悄失效。

**建议**：用显式方言层替代正则（每张表/每类查询直接写两套 SQL，或用 query builder），至少先在替换前剥离字符串字面量与注释。

---

### P1-1 数据库访问在主线程同步阻塞，且 MariaDB 只有单连接

**位置**：`mariadb-compat.mjs:129-137` 的 `call()` 用 `Atomics.wait` 阻塞主线程最长 10 秒；`mariadb-worker.mjs:8` 使用 `mysql.createConnection`（单连接，非连接池）。

**基准证据**（本地，seed 数据）：

| 场景 | 单请求 | 并发 40 中位数 |
|---|---|---|
| `GET /` | 32ms | 123ms |
| `GET /api/v1/tools?limit=24` | 3.9ms | 62ms |
| `GET /api/v1/health` | 25.5ms | 47ms |

**影响**：

- 每个请求的每次 DB 操作都会冻结事件循环，所有并发请求被串行化；测试中工具列表延迟放大 15 倍。
- 单连接意味着即使换成异步，吞吐仍受一条 TCP 连接限制。
- 一旦出现慢查询（最长 10 秒超时），整站阻塞 10 秒，健康检查也会超时，可能被负载均衡摘除。
- `getUserBySession` 每个请求至少 2 次查询（session + avatar + email 验证），且每 5 分钟写一次 `last_seen_at`，进一步放大阻塞次数。

**建议**：改为异步 `mysql2/promise` 连接池，业务层 `await`；去掉 `Atomics` 兼容层。这是从"能跑"到"能扛"的关键改造。

---

### P1-2 限流桶耗尽时拒绝所有新 key

**位置**：`rate-limiter.mjs:10-13`

```js
if (!current && buckets.size >= maxBuckets) {
  for (...) if (bucket.resetAt <= time) buckets.delete(...);
  if (buckets.size >= maxBuckets) throw rejected();   // 对"新访客"直接 429
}
```

**复现证据**：把 `maxBuckets` 设为 50，填满后请求一个全新 key → `429 rate_limited`。

**影响**：桶一旦被有效 key 填满（生产 5000），**所有新访客**在下一次过期扫描前都会被拒绝，而不是淘汰最旧桶。攻击者用大量来源 IP 或渠道参数即可把全站推入 429 状态；正常流量高峰（例如投放）也可能触发。

**建议**：改为淘汰最旧/最少使用的桶；或按 key 前缀分组限额，桶满时降级为"宽松模式"而非直接拒绝。

---

### P1-3 分享链接解析的全局单例锁

**位置**：`link-extract.mjs:42,50`

```js
let parsing = false;
...
if (parsing) throw new Error('已有一条链接正在解析，请稍后再试。');
```

**影响**：全站同一时刻只能有一个解析任务，超时上限 `publicMode ? 120s : 600s`。生产环境 `publicMode` 默认为开（`server.mjs:1243`），任意一个登录用户发起解析后，其他所有用户在此后最长 120 秒内全部收到"已有一条链接正在解析"。这是单用户即可触发的全局可用性故障。

**建议**：改为按用户并发限制 + 全局队列（如最多 4 并发），超限排队而非直接报错。

---

### P1-4 反向代理头契约不一致，限流与审计 IP 失真

**位置**：`server.mjs:1352-1359` 的 `getIp` 只认 `X-Forwarded-For`，且要求 `NIKE_TRUST_PROXY=true` 且直连地址为回环地址；而 `deploy/nikai-nestdutio.nginx.conf` 只设置了 `X-Real-IP`。

**影响**：

- 若主站 nginx 未设置 `X-Forwarded-For` 或未开启 `NIKE_TRUST_PROXY`，所有请求的 `ip` 都是 `127.0.0.1`，**全站共用一个限流桶**（`ip:read` 120/分钟），正常流量会互相挤占，且封禁/审计无法定位真实来源。
- 反之若代理链路配置错误（例如覆盖而非追加 XFF），客户端可伪造 IP 绕过限流。
- 这套契约目前只存在于代码里，`docs/` 与 `deploy/` 都没有对应的主站 nginx 片段。

**建议**：固定一套契约（推荐 nginx 设置 `X-Forwarded-For $proxy_add_x_forwarded_for` + `X-Forwarded-Proto $scheme`），启动时校验 `NIKE_TRUST_PROXY` 与监听地址的一致性，并把主站 nginx 配置纳入 `deploy/`。

### P1-5 测试基线未更新，CI 变红

**全量执行结果**：`tests 772 / pass 760 / fail 9 / skipped 3`，耗时 5 分 37 秒。

- **2 项真实回归**：`tests/api.test.mjs:166` 与 `tests/import.test.mjs:48` 断言迁移数为 39，实际为 40（新增 `040_nestdutio_progress.sql` 未同步基线）。
- **7 项环境性失败**：`tests/mariadb-operations.test.mjs` 调用 `spawnSync(bash)`，在 Windows 上 `ENOENT`；Linux CI 应可通过，但说明测试不可跨平台。

**影响**：CI 长期红着，等于没有门禁；真实回归与噪音混在一起，团队会逐渐忽略测试结果。这也解释了工作区为何积累 27+ 个未提交文件。

**建议**：改正迁移计数断言（改为读取 migrations 目录长度或只断言 `>= 40`）；MariaDB 脚本类测试加 `process.platform !== 'linux'` 跳过；让主干恢复绿色后再谈覆盖率。

### P2-1 CSP 允许已无引用的 unpkg.com

`server.mjs:406` 默认策略为 `script-src 'self' https://unpkg.com`，但全仓已无任何 unpkg 引用（grep 结果为空）。等于给全站开了一个不需要的第三方脚本执行通道，一旦 unpkg 上的依赖被投毒即可在全站执行任意脚本。建议直接移除。

---

### P2-2 静态文件全同步 I/O，缓存容量不足

`serveStaticFile` 每次请求都执行 `statSync`，小文件再 `readFileSync`（`server.mjs:432-499`）；`staticCacheMaxEntries = 64`，而 `public/` 下有 425 个资源。

实测首页并发 40 时中位延迟从 32ms 升到 123ms，主要来自同步读盘与 `gzipSync` 的串行化。建议：`fs/promises`、缓存上限提升到覆盖工作集、构建期预压缩（`.gz`/`.br`）、静态资源加内容指纹并使用 `immutable` 长缓存（目前统一 `max-age=300`，CDN 命中率低）。

---

### P2-3 首页与工具页资源体积偏大

| 资源 | 体积 | 说明 |
|---|---|---|
| `public/assets/vendor/ffmpeg/ffmpeg-core.wasm` | 30.7MB | 仅视频工具页需要，需确认不预加载 |
| `public/games/` | 19MB | 含 multiple 未压缩 three.js 与模型文件 |
| `public/assets/home/ai-companion.png` | 0.9MB | 首页首屏图，未转 WebP/AVIF |
| `public/assets/home/assistant-wave.png` | 0.7MB | 同上 |
| `public/brand-icon.svg` | 0.6MB | 图标级 SVG 体积异常，疑似内嵌位图或未清理路径 |

建议：PNG 转 WebP/AVIF 并加 `srcset`；SVG 走 svgo 清理；wasm 与 games 静态资源独立域名或懒加载；对 `brand-icon.svg` 做一次体积审计（0.6MB 的 SVG 每次首屏都要下载）。

---

### P2-4 关键状态全部驻留进程内存

`recentRequests`、`monitoringCache`、`imageResults`、限流桶、链接解析票据都在单进程内存中。后果：无法水平扩展（多实例下限流各算各的、监控失真、图片结果在另一实例 404）；重启后进行中的生图任务被 `imageJobs.recover()` 统一标记失败。

如果近期没有扩容计划，这一条可以接受，但应在架构文档里写明"单实例假设"，避免未来误加实例。

---

### P2-5 错误处理缺少兜底与响应状态判断

- 全仓没有 `process.on('unhandledRejection')` / `uncaughtException`（grep 为空），这是 P0-1 能升级为进程退出的直接原因。
- `sendProblem`（`server.mjs:369-384`）不判断 `response.headersSent`，若在流式响应中途抛错会二次抛 `ERR_HTTP_HEADERS_SENT`；`link-extract` 已单独规避，其他路径没有。
- 非 `HttpError` 一律落到 500 且 `code=internal_error`，前端无法区分"上游超时"和"代码 bug"。

建议：加进程级兜底（记录后优雅退出）+ `sendProblem` 增加 `headersSent` 判断 + 建立错误码目录（目前散落在各模块字符串里）。

---

### P2-6 可观测性偏薄

只有 `console.log` 单行 JSON（含 `request_id`，这点做得对），没有日志级别、没有慢查询记录、没有 Prometheus 指标。`/api/admin/v1/monitoring` 返回的是进程内存快照，重启即清零。建议接入 pino（带级别与采样）+ 暴露 `/metrics`（QPS、P95、DB 耗时、限流命中、任务队列深度）。

---

### P2-7 密码与会话策略偏弱

- `readPassword`（`validation.mjs:99-104`）只校验长度 10-128，无复杂度、无弱口令/泄露库比对。
- 会话固定 30 天（`auth.mjs:6`），无轮换、无设备列表、无"退出所有设备"；管理员账号也没有 MFA。
- 好的一面：scrypt + 随机盐 + 恒定时间比较 + 用户不存在时用假盐对齐耗时，实现是规范的。

---

### P2-8 注册接口泄露邮箱是否已注册

`server.mjs:1935` 在邮箱已存在时返回 409 `email_registered`，可用于批量探测账号。登录接口的提示是统一的（正确做法），注册侧不一致。建议改为统一文案 + 邮件通知，或加验证码前置（目前验证码已在注册前校验，实际可利用性有限，故定为中低）。

## 四、分维度小结

### 4.1 代码结构与质量

分层清晰：`server.mjs`（路由/模板）、`backend/*`（领域服务）、`backend/nestdutio`（子应用）、`backend/migrations`（40 个增量迁移），每个模块职责基本单一，依赖注入（`options.fetchImpl`、`now`、`lookup`）用得规范，测试可替换性强。

主要问题：
1. `server.mjs` 2664 行同时承担路由分发、SEO 模板、静态文件服务、安全头，继续增长会失控，建议按 `routes/`、`views/`、`static/` 拆分。
2. 超长单行与一行式业务逻辑（P2-9）。
3. `mariadb-compat.mjs` 的"SQL 方言翻译器"是结构性技术债（P0-3、P1-1 都源于它），建议单独立项替换。

### 4.2 安全性

做得好的部分（值得保留）：

- SQL 全部参数化，动态拼接只出现在白名单表名/字段名（`hydrateTools`、`listTools` 的 `orderBy` 映射）。
- 密码 scrypt + 随机盐 + `timingSafeEqual`，用户不存在时用假盐对齐耗时。
- 会话只存 `sha256(token)`，Cookie `HttpOnly + SameSite=Lax`，生产自动加 `Secure`。
- 平台 API Key 用 AES-256-GCM 加密落库，接口只回 `****` + 尾 4 位。
- SSRF 防护是全仓质量最高的部分：`safeFetch` 做 DNS 预解析、私网段阻断、连接地址固定（防 DNS rebinding）、跨域重定向带凭证直接拒绝。
- 上传做魔数校验 + 随机文件名 + SVG 安全检查；multipart 手写解析有边界、字段数、大小三重限制。
- 生产依赖 `npm audit` 为 **0 漏洞**。

需要修的部分：P0-1（进程崩溃）、P1-2（限流全局误伤）、P1-4（代理头）、P2-1（多余 CSP 源）、P2-7/P2-8（账号策略）。

### 4.3 性能瓶颈

按影响排序：

1. **数据库同步阻塞 + 单连接**（P1-1）——决定并发上限。
2. **静态文件同步 I/O 与小缓存**（P2-2）——首页并发放大 4 倍。
3. **首页重资源**（P2-3）——30.7MB wasm、0.9MB PNG、0.6MB SVG。
4. **同步 gzip**（P3-5）与 **bootstrap 无缓存**（每次重建）。
5. **`serializeUser` 的 N+1**：`listUsers` 每个用户额外 2 次查询，管理端用户多时明显（低优先）。

单请求延迟本身很好（健康检查 25ms、列表 4ms），问题集中在"并发时的排队"，不是"单次太慢"。

### 4.4 错误处理

- 业务错误用 `HttpError(status, code, message, details)` 统一，`details.settlement` 这种资金态透传处理得很细。
- 上游调用普遍带 `AbortSignal.timeout`，超时映射到 504，分类到位。
- 缺的是**进程级兜底**（P2-5）与**响应状态判断**，以及错误码缺少集中目录。

### 4.5 可维护性

优势：772 个测试用例、模块化迁移、发布脚本具备独占锁/干净目录预检/数据库+代码快照/健康检查/自动回滚，工程化程度高于同类自建站。

短板：无 lint/类型（P2-9）、测试红（P1-5）、文档漂移（P2-10）、脏工作区、以及 MariaDB 兼容层这种"看起来能跑但语义不可靠"的抽象。
